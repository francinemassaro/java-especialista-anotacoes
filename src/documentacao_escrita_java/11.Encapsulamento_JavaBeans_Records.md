# Encapsulamento, Boas Práticas e JavaBeans

## 1) O problema da falta de encapsulamento

Apesar de normal criarmos classes especificamente para representação de dados, e colocar a lógica apenas em classes de serviço, é importante avaliar o risco. Pois a falta de encapsulamento nesse caso, faz com que qualquer parte do código possa chamar a classe e mudar um atributo diretamente, mesmo que não seja condizente com as regras de negócio.

**Exemplo:**  
Tenho uma classe Cartão, do qual o saldo nunca pode ser negativo.  
Embora nas services que usam o saldo do cartão, seja possível validar e enviar um exception caso por ventura o gasto ou mau uso de cartão faça ele ter o saldo negativo causando o erro na aplicação, a falta de encapsulamento não previne de sertarmos um valor direto, como por exemplo `Cartao.saldo = -700;`  
Sendo assim, a falta de encapsulamento nesse caso consta uma má prática e risco.

## 2) Implementando encapsulamento

Encapsulamento é uma técnica para esconder informações internas de uma classe, para que ele não seja exposto ou alterado por outras classes.  
Atributos da classe, sempre devem ser criados com o método de acesso privados. Muito raramente terá um criado como public.

Como boa prática, criar getter e setter dos atributos e não só isso, adicionar lógica quando a regra for 100% direcionada a própria classe. Isso evita por exemplo uma replicação de código e ter que procurar em muitos lugares caso alguma regra envolvendo a própria classe seja alterado.

**Exemplo:**  
Em uma classe `Cartao` onde temos saldo, e que o saldo não pode nunca ser negativo, faz todo sentido criar um encapsulamento do set, para que nunca altere para um valor negativo.

Outro exemplo usando a classe `Cartao`: em caso de uma regra onde temos na classe saldo e tarifa de 10 centavos por depósito, faz sentido que ao alterar o saldo a tarifa já seja descontada dentro da própria classe `Cartao` ao invés de um serviço.  
Assim, em caso de alteração futura, onde não seja mais necessário uma taxa a cada depósito, podemos exclui-la diretamente na classe `Cartao` ao invés de procurar todos os cenários de serviços envolvendo deposito (como por exemplo, essa repetição em uma classe de Pix, de Transferencia, de Cheque).

## 3) JavaBeans e métodos getters e setters

De forma bem resumida, um JavaBean é um componente Java que segue a especificação JavaBean. Isto significa dizer, que são componentes de software que definem algumas características, como por exemplo:

1. Possuem um construtor sem argumentos.
2. Implementam `java.io.Serializable`.
3. Definem métodos get/set para acesso às suas propriedades.
4. Definem métodos add/remove para manipular listeners.
5. São thread-safe (Garantir que a troca de informações entre esses componentes seja segura e com garantias da informação).

No entanto, as 3 primeiras características por si só já poderiam fazer com que consideremos o componente como um JavaBean (inclusive em mercado as vezes chamam de JavaBean classes apenas com getters e setters).

**Importante:**  
Não são as anotações de uma classe que definem um JavaBean e sim as características da mesma.

A título de exemplo, temos uma lib que podemos utilizar no Java conhecida como **Lombok**. Esta lib, define anotações para gerar, por exemplo, um construtor vazio e os métodos getters e setters. Se utilizar esta lib e essas anotações em sua classe, ainda fazendo com que a mesma implemente `java.io.Serializable`, já poderíamos dizer que trata-se de um JavaBean.

Contudo, perceba que estamos utilizando anotações que evitam a escrita de código boilerplate, mas que nos fornecem características de um JavaBean. O que quero dizer neste caso, que não são as anotações que definem este tipo de componente e sim as características do mesmo.

> No caso de setter, avaliar se faz sentido criar de todos os atributos. Afinal, se criar um setter direto de saldo por exemplo, ele continua exposto na aplicação.

## 4) Boas práticas: use métodos de acesso em classes públicas (incluindo Tell Don't Ask)

Reforçando o uso de encapsulamento e como é importante deixar variáveis de classe pública privadas e criar os métodos de acesso getters e setters.

**Tell Don't Ask**  
Seria tipo um princípio que reforça esse comportamento. Diz que a classe precisa ter não apenas dados, mas comportamento.

**Observação interessante da aula:**  
Suponha uma classe `Horario` que recebe minuto e hora. Se um dia alterarmos de minuto e hora, para um array de dois parâmetros, conseguimos alterar os métodos getters e setters apenas, e não mexer em mais nada. Isso deixa o código protegido, e evita de ter que mexer em diversas partes.

```java
public class Horario {

    private int[] valores = new int[2];
    // private int hora;
    // private int minuto;

    public Horario(int hora, int minuto) {
        setHora(hora);
        setMinuto(minuto);
    }

    public int getHora() {
        // return hora;
        return valores[0];
    }

    public void setHora(int hora) {
        if (hora < 0 || hora > 23) {
            throw new IllegalArgumentException("Hora inválida: " + hora);
        }
        // this.hora = hora;
        this.valores[0] = hora;
    }

    public int getMinuto() {
        // return minuto;
        return valores[1];
    }

    public void setMinuto(int minuto) {
        if (minuto < 0 || minuto > 59) {
            throw new IllegalArgumentException("Minuto inválida: " + minuto);
        }
        // this.minuto = minuto;
        this.valores[1] = minuto;
    }

    public String formatar() {
        return String.format("%dh%dm", getHora(), getMinuto());
    }
}

public class Principal {
    public static void main(String[] args) {
        Horario horario = new Horario(10, 55);
        System.out.println(horario.formatar());
    }
}
```

## 5) Código limpo: Lei de Demeter (incluindo Train Wreck)

**Code Smells / Anti-patterns**: Parece ser legal mas não é.  
O que acontece com chamada encadeada... também conhecido como **Train Wreck** (acidente de trem por conta dos "vagões" que perdem o controle e batem).

**Exemplo ruim:**
```java
locacao.getVeiculo().getGroup().getValorDiaria();
```

**Problemas:**
- Dificulta a leitura do código.
- Aumenta acoplamento de código.
- Exige conhecimento das classes intermediárias.
- Expõe detalhes desnecessários de outras classes.
- Alterações intermediárias podem quebrar o código todo.

**Correção:**  
Colocar um método em cada classe para retornar apenas o que ela conhece.

**Exemplo bom:**
```java
locacao.getDiarias(); // internamente busca o valor e a origem
```

Essa prática é muito ligada ao **"Tell Don't Ask"**.

> Importante: Embora Demeter ajude, pode gerar muitas funções e poluir a classe. É considerado uma "grey area".

## 6) Boas práticas: não permita instanciação com construtor privado

Se uma classe possui apenas métodos estáticos e esse é o papel dela, não faz sentido que ela seja instanciada.  
Logo, criar um construtor privado para impedir que ela seja instanciada e seja possível apenas chamá-la direto.

## 7) Boas práticas: crie cópias defensivas

Cópia defensiva é uma técnica usada para proteger o estado interno de um objeto, impedindo que código externo modifique suas variáveis diretamente.

Ela cria uma cópia segura dos dados ao retornar ou receber objetos mutáveis, como listas ou datas.

### 💥 Exemplo do problema (sem cópia defensiva):
```java
public class Pessoa {
    private List<String> telefones;

    public List<String> getTelefones() {
        return telefones; // expõe lista interna!
    }
}

Pessoa p = new Pessoa();
p.getTelefones().add("9999"); // modifica o objeto por fora!
```

### ✅ Exemplo com cópia defensiva:
```java
public List<String> getTelefones() {
    return new ArrayList<>(telefones); // devolve cópia!
}

public void setTelefones(List<String> telefones) {
    this.telefones = new ArrayList<>(telefones); // armazena cópia!
}
```

**Quando usar:**
- Sempre que armazenar ou devolver objetos mutáveis.
- Protege contra efeitos colaterais.
- Ajuda a manter imutabilidade e integridade de dados.

## 8) Boas práticas: minimize a mutabilidade (incluindo Value Object)

**Imutabilidade** = 1 valor por cada instância.  
Não dá pra alterar valor da mesma instância sem criar uma nova.

**Para ser imutável:**
- Variáveis `private final`
- Sem setters
- Valor atribuído apenas via construtor

**Value Object**: Objeto que só representa um valor.

**Desvantagem**:  
Sempre que precisar alterar o valor, precisa instanciar uma nova.

**Exemplo**: Uma `CorAzul` será sempre azul. Se quiser outra cor, cria uma nova.

> Vai alterar? Deixe sem `final`  
> Não vai alterar? Use `final`

Reduzir mutabilidade → reduz chance de bugs.

## 9) Records

**Records** são usados quando precisa de uma classe de representação, e os valores não vão mudar.

Possui as mesmas características de uma classe imutável, mas sem precisar escrever todos os métodos manualmente.

- Já é implicitamente `final`
- Cria atributos `private final`
- Cria getters automáticos

**Exemplo:**
```java
public record Horario(int hora, int minuto) {
}
```

> Ao chamar `horario.hora()` está acessando o getter implícito.
